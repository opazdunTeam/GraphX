# Контракты GraphX

В этом каталоге находятся машиночитаемые договоры между компонентами GraphX. Документация объясняет смысл и жизненный цикл данных, а файлы в `contracts` точно задают их переносимую форму.

## Структура

```text
contracts/
  openapi.yaml                 REST API между Go и web
  schemas/
    messages/                  сообщения RabbitMQ
    ingestion/                 результаты адаптеров и общие ingest-типы
  examples/
    messages/                  примеры полных сообщений
    ingestion/                 примеры содержимого manifest
```

### HTTP API

- `openapi.yaml` - описание REST API, предоставляемого Go-приложением для web-клиента.

Общие HTTP-контракты MVP:

| Область           | Операции                                                      |
| ----------------- | ------------------------------------------------------------- |
| Состояние API     | liveness и readiness                                          |
| Источники         | каталог доступных источников                                  |
| Расследование     | создание, чтение, статус и отмена                             |
| Сопоставление     | список reviews, просмотр кандидатов, решение и отмена решения |
| Знания            | сущности, граф, временная шкала и фактическая связь           |
| Управление сбором | явное расширение ветви от выбранной сущности                  |
| Доказательства    | полное происхождение claim и открытие исходного artifact      |

Все эти операции описаны в `openapi.yaml`. Контракты конкретных ICIJ, KASE и других источников остаются внутри соответствующих адаптеров и не становятся частью общего API GraphX.

### Сообщения RabbitMQ

- `schemas/messages/message-envelope.v1.schema.json` - общий конверт сообщения;
- `schemas/messages/source-query.v1.schema.json` - переносимый запрос человека или организации;
- `schemas/messages/source-collect-requested.v1.schema.json` - команда на сбор данных (от Go к worker);
- `schemas/messages/source-collect-completed.v1.schema.json` - возврат успешного результата (от worker к Go);
- `schemas/messages/source-collect-failed.v1.schema.json` - возврат ошибки и уже сохранённых материалов (от worker к Go).

### Ingest

- `schemas/ingestion/artifact-reference.v1.schema.json` - ссылка на неизменяемый материал;
- `schemas/ingestion/source-record.v1.schema.json` - запись во внутренней форме источника;
- `schemas/ingestion/claim.v1.schema.json` - атомарное утверждение с доказательством и временем;
- `schemas/ingestion/source-result.v1.schema.json` - успешный результат сбора;
- `schemas/ingestion/source-result-manifest.v1.schema.json` - содержимое крупного результата, сохранённого в MinIO.

Это полный набор межкомпонентных JSON Schema для MVP.

## Как читать контракты

Все JSON Schema используют стандарт редакции Draft 2020-12. Поле `type` определяет вид сообщения, а `schema_version` - версию его конверта. Несовместимое изменение получает новый суффикс в `type` и отдельный файл, например `source.collect.requested.v2`.

Схема проверяет структуру и простые ограничения. Правила, зависящие от нескольких объектов или состояния системы, остаются в коде. Например, consumer дополнительно проверяет, что локальные ссылки claim существуют в records, номер попытки актуален, а классификация ошибки соответствует её коду.

Форматы `uuid`, `date`, `date-time` и `uri` должны проверяться валидатором с включённой поддержкой `format`.

## Режимы результата

Небольшой результат передаётся прямо в `source.collect.completed.v1`. Крупный результат сохраняется в MinIO по схеме `source-result-manifest.v1.schema.json`, а сообщение содержит ссылку на него вместо records и claims. Эти режимы не смешиваются. Manifest не заменяет исходные материалы: их ссылки остаются в `artifacts`.

Примеры в `examples` поясняют форму данных, но не заменяют схемы. Они станут входными данными контрактных тестов при реализации publisher, workers и consumer.

## Как контракты входят в код

| Контракт              | Использование в GraphX                                                                |
| --------------------- | ------------------------------------------------------------------------------------- |
| `openapi.yaml`        | Генерация Go HTTP-типов, серверного интерфейса и Gin-адаптера через `oapi-codegen`    |
| `openapi.yaml`        | Генерация TypeScript-типов web-клиента через `openapi-typescript`                     |
| Message JSON Schema   | Проверка входящих RabbitMQ-сообщений в Go consumer и контрактные тесты publishers     |
| Ingestion JSON Schema | Проверка результата worker, manifest и общих переносимых типов                        |
| `examples`            | Общие fixtures для Go- и Python-контрактных тестов, а также понятные человеку образцы |

OpenAPI является источником генерируемого transport-кода, но не бизнес-логики. JSON Schema в MVP не используются для генерации Pydantic или Go моделей: модели остаются небольшими и явными, а схемы независимо проверяют их сериализованное представление.

Условия OpenAPI вроде `oneOf` и temporal `if/then` должны по возможности сохранять полезные типы при генерации, но сгенерированный код не считается runtime-валидатором всей предметной семантики. CI проверяет, что `SubjectInput` остаётся явным union без `unknown`, необязательные request limits не становятся обязательными, а Go и TypeScript генераторы принимают один контракт. Условия precision, snapshot, state transition и optimistic locking повторно проверяются на HTTP/domain слое.

Сгенерированные файлы фиксируются в репозитории и не редактируются вручную. Go и web имеют локальные check-команды, которые повторяют генерацию, обнаруживают stale output и проверяют ключевую форму типов. Изменение контракта считается завершённым, когда обновлены схема, пример, generated code и затронутые границы. Runtime/domain validation остаётся ручным кодом и не подменяется генерацией.

AsyncAPI пока не добавляется: он будет полезен после стабилизации exchanges, routing keys и первой рабочей реализации сообщений.
