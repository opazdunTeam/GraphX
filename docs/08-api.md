# HTTP API

## Общие правила

- базовый путь - `/api/v1`;
- JSON в UTF-8;
- идентификаторы - UUID;
- время - ISO 8601 с часовым поясом;
- ошибки возвращаются в едином JSON-формате `application/problem+json` с кодом, названием и понятным описанием;
- большие списки используют cursor pagination;
- изменяющие команды поддерживают `Idempotency-Key` там, где повтор опасен.
- API принимает необязательный `X-Request-ID` и возвращает фактически использованный идентификатор в каждом ответе; небезопасное или слишком длинное значение заменяется новым.

OpenAPI описывает согласованный HTTP API между Go и web. Операция может быть зафиксирована в спецификации до появления handler; фактическую готовность подтверждают код и тесты. JSON Schema используется отдельно для сообщений RabbitMQ и ingest-данных: это другой транспорт и другой жизненный цикл версий.

OpenAPI содержит весь согласованный HTTP-контракт MVP, но наличие операции в спецификации не означает готового handler. Реализация начинается с первого вертикального среза.

## Первый вертикальный срез

| Метод и путь                       | Назначение                                 |
| ---------------------------------- | ------------------------------------------ |
| `POST /investigations`             | Создать расследование                      |
| `GET /investigations/{id}`         | Получить его основные данные               |
| `GET /investigations/{id}/status`  | Получить ход работы и состояния источников |
| `POST /investigations/{id}/cancel` | Отменить расследование                     |
| `GET /claims/{id}/evidence`        | Получить полное происхождение утверждения  |
| `GET /artifacts/{id}/content`      | Открыть сохранённый исходный материал      |
| `GET /sources`                     | Получить доступные источники               |

Health endpoints также входят в первый контракт, но работают без префикса `/api/v1`.

В Go служебные и бизнес-маршруты регистрируются раздельно. Health endpoints остаются ручными маршрутами корневого router. Конфигурация `oapi-codegen` исключает тег `health`, а сгенерированный Gin-адаптер содержит только бизнес-операции и подключается с `BaseURL: "/api/v1"`. Так path-level `servers: /` остаётся корректной частью OpenAPI для клиентов, но runtime не зависит от поддержки этого override серверным генератором и не создаёт дубли `/api/v1/health/*`.

## Остальные endpoints MVP

| Метод и путь                         | Назначение                      |
| ------------------------------------ | ------------------------------- |
| `GET /investigations/{id}/reviews`   | Получить спорные совпадения     |
| `GET /reviews/{id}`                  | Получить review и кандидатов    |
| `POST /reviews/{id}/decision`        | Выбрать кандидата или ни одного |
| `POST /reviews/{id}/decision/revert` | Отменить решение                |

| `GET /entities/{id}`                 | Получить карточку сущности      |
| `GET /investigations/{id}/graph`     | Получить компактный граф DTO    |
| `GET /investigations/{id}/timeline`  | Получить временную шкалу        |
| `GET /relationships/{id}`            | Получить связь и её обоснование |

`GET /sources` возвращает общий каталог: код, название, доступность, режим работы, роли, поддерживаемые типы сущностей и пассивно наблюдаемое состояние. Он не раскрывает credentials, внутренние URL и настройки адаптера.

## Создание расследования

Запрос содержит вид исходного subject и хотя бы имя либо один известный идентификатор. Дополнительно передаются безопасные лимиты: глубина, число сущностей и при необходимости непустой список источников. API проверяет выбранные источники до создания расследования. Расследование, первое задание и outbox создаются одной транзакцией, поэтому успешный ответ `202 Accepted` возвращает состояние `running`, идентификатор и ссылку на status.

## Статус

Status читается только из PostgreSQL и не опрашивает workers напрямую. Он возвращает:

- общий status и stage;
- `state_version`;
- число известных и достигших конечного состояния заданий без вычисления ложного процента;
- агрегированное состояние каждого источника;
- частичные ошибки;
- число открытых reviews, ссылку на их список и отдельные действия по источникам.

API не возвращает внутренний список `source_jobs` как read model. Состояние источника агрегируется по всем его заданиям в расследовании. Пока есть незавершённые задания, используется приоритет `action_required` → `running` → `retry_wait` → `pending`. Когда все задания завершены:

- успех без ошибок даёт `succeeded`;
- успех вместе с `failed` или `unavailable` даёт `completed_partial`;
- только корректные пустые ответы дают `not_found`;
- отсутствие полезного результата при недоступности даёт `unavailable`;
- постоянная или системная ошибка без полезного результата даёт `failed`;
- полностью отменённая работа даёт `cancelled`.

Вместе со статусом возвращаются количества активных, известных и завершённых заданий, общее число попыток, следующая попытка и последняя безопасная ошибка.

`requires_action` истинно, если существует хотя бы один открытый review или действие по источнику. Единого `action_url` расследования нет: reviews открываются через общий `reviews_url`, а действия источников возвращаются отдельным списком с `job_id`, кодом, описанием и собственной необязательной ссылкой.

## Решение пользователя

Список reviews и список сущностей используют cursor pagination. Краткий review не переносит всех кандидатов; полная операция `GET /reviews/{id}` возвращает исходную запись с проверяемыми атрибутами, кандидатов, признаки, конфликты и последнее решение.

Команда содержит `expected_version`, решение `select_candidate` либо `none_of_above`, обязательное nullable-поле `candidate_id` и при необходимости причину. Для `select_candidate` идентификатор кандидата обязателен, для `none_of_above` он равен `null`. Несовпадение версии возвращает `409 Conflict`, чтобы два открытых окна не затёрли решения друг друга.

Выбор кандидата может автоматически запланировать enrichment, но это должно быть частью одной понятной бизнес-команды, а не скрытым действием интерфейса.

## Polling

Для MVP достаточно polling status примерно раз в 2–3 секунды с jitter. В неактивной вкладке интервал увеличивается до 10–15 секунд, после терминального состояния запросы прекращаются. Позже можно добавить weak ETag, а SSE - только если polling действительно создаст проблему. SSE должен передавать уведомление об изменении, а не становиться вторым источником состояния.

## DTO графа

API возвращает не таблицы базы, а компактную модель: nodes, factual edges, derived edges, hypotheses, краткие evidence summaries и признаки неполноты. По умолчанию возвращаются только фактические связи; вычисленные связи и гипотезы включаются отдельными query-параметрами. Фактическое ребро содержит `relationship_id`; вычисленное - код и версию правила, объяснение и supporting ids; гипотеза возвращается отдельно и не выдаётся за факт. Полные claims и artifacts загружаются по требованию.

Timeline возвращает события, интервалы и снимки с теми же precision и temporal basis, что хранятся в claims. Интерфейс не должен мутировать дату-якорь в более точную дату.

Карточка сущности возвращает подтверждённые варианты имени, идентификаторы и атрибуты со ссылками на claims. Фактическая связь возвращает стороны, роли, долю, временной интервал и минимум одно доказательство.

## Доказательства и исходные материалы

Evidence DTO показывает всю проверяемую цепочку: claim, source record, версии обработки, artifact, locator и короткий excerpt. Для claim возвращаются исходное и нормализованное значения, qualifiers и временные поля. Внутренний object key MinIO наружу не передаётся.

`GET /artifacts/{id}/content` отдаёт неизменяемое содержимое через Go API с исходным media type. В OpenAPI ответ описан диапазоном `*/*`, потому что фактический `Content-Type` берётся из зарегистрированного artifact. SHA-256 передаётся как корректный strong `ETag` в кавычках. Это сохраняет контроль доступа в одном месте и не связывает web с MinIO. Позднее реализацию можно заменить временной подписанной ссылкой без изменения evidence DTO, если `content_url` останется стабильной ссылкой API.

Сгенерированные Go и TypeScript типы проверяют переносимую структуру DTO, но не исполняют все условные правила JSON Schema/OpenAPI. HTTP boundary отдельно выполняет runtime-валидацию входной формы, а предметный слой проверяет temporal anchors, snapshot semantics, optimistic locking, limits и допустимость переходов состояния. Генерация кода не заменяет эти проверки.

## Ошибки и идентификатор запроса

Problem response всегда содержит `type`, `title`, HTTP `status`, машинный `code` и безопасный понятный `detail`. Диагностические подробности, секреты, ответы источников и stack trace клиенту не возвращаются.

Клиент может передать `X-Request-ID` длиной до 128 символов из латинских букв, цифр и знаков `._:-`. Если заголовок отсутствует или не проходит проверку, API создаёт новый. Фактически использованный идентификатор возвращается во всех успешных ответах и ошибках.
