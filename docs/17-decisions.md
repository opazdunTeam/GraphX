# Принятые решения

Этот файл - единый журнал основных продуктовых и технических договорённостей. Причины решения должны быть понятны без чтения всей документации. Если решение меняется, старая запись не удаляется, а помечается как заменённая с указанием нового решения.

| №   | Решение                                                | Почему                                                                                        |
| --- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 1   | Модульный монолит на Go                                | Меньше эксплуатационной сложности при понятных внутренних границах                            |
| 2   | Gin только как HTTP-адаптер                            | Простая доставка HTTP без зависимости предметной логики от framework                          |
| 3   | PostgreSQL - источник истины                           | Транзакции, SQL, JSONB и `pg_trgm` закрывают потребности MVP                                  |
| 4   | `pgx`, ручной SQL и goose                              | Схема и запросы остаются явными, без тяжёлого ORM                                             |
| 5   | Один Python-пакет workers                              | Удобная экосистема источников без преждевременного набора сервисов                            |
| 6   | Workers не имеют доступа к PostgreSQL                  | Один владелец бизнес-состояния и меньше скрытой связанности                                   |
| 7   | RabbitMQ и доставка at least once                      | Долгие обращения выполняются асинхронно, повторы безопасны через идемпотентность              |
| 8   | Transactional outbox и inbox                           | Транзакция БД не может атомарно охватить RabbitMQ                                             |
| 9   | `source_jobs` не является очередью                     | Таблица хранит бизнес-состояние, RabbitMQ - состояние доставки                                |
| 10  | MinIO для неизменяемых artifacts                       | Повторный разбор возможен без нового запроса к источнику                                      |
| 11  | Версионированная обработка                             | Parser, mapper и normalization можно улучшать без потери истории                              |
| 12  | Два этапа: discovery и enrichment                      | Ошибка первоначального совпадения не должна разрастаться по графу                             |
| 13  | Candidate generation отдельно от decision              | Поиск кандидатов и решение о тождестве имеют разную семантику и метрики                       |
| 14  | `pg_trgm` для кандидатов MVP                           | Достаточно для первого измеримого решения без отдельного поискового сервиса                   |
| 15  | Решения о совпадениях отменяемы                        | Ошибочное объединение неизбежно и не должно портить историю необратимо                        |
| 16  | Facts, derived relations и hypotheses разделены        | Пользователь всегда понимает, что сообщил источник, а что вычислила система                   |
| 17  | Snapshot не означает непрерывный интервал              | Иначе граф создаст ложную историю между двумя наблюдениями                                    |
| 18  | REST/JSON и OpenAPI                                    | Простой контракт web и Go API                                                                 |
| 19  | JSON Schema для сообщений и ingest                     | HTTP и очередь версионируются независимо                                                      |
| 20  | Polling на MVP                                         | Проще SSE и достаточно для небольшого числа пользователей                                     |
| 21  | Vue 3, Vite, TypeScript и pnpm                         | Подходящий SPA-стек без ненужного SSR                                                         |
| 22  | Docker Compose и Nginx для возможного VPS              | Достаточно для учебного MVP и маленькой команды                                               |
| 23  | Развёртывание выполняется в конце                      | Сначала проверяется аналитическое ядро                                                        |
| 24  | Нет Neo4j, Redis, Kafka, Kubernetes и обязательной LLM | Для MVP нет измеримой проблемы, оправдывающей эту сложность                                   |
| 25  | Источники подключаются последовательно                 | Fixture, ICIJ и KASE сначала проверяют весь контур и временную модель                         |
| 26  | Пять источников - план, а не условие демонстрации      | Состав и порядок можно менять по результатам разработки                                       |
| 27  | Пассивное наблюдение за источниками важнее частых ping | Оно отражает реальную работоспособность и не расходует квоты                                  |
| 28  | Внутренняя авторизация не входит в MVP                 | Локальная сеть или небольшой внешний слой доступа достаточны для учебной демонстрации         |
| 29  | Вычисленные связи в MVP строятся при чтении            | Они остаются отдельными от фактов и не требуют преждевременной таблицы или отдельного сервиса |
