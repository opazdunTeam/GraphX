# Временная модель

## Разные виды времени

У одного факта может быть несколько дат с разным смыслом:

- `valid time` - когда факт был верен в реальном мире;
- `event time` - когда произошло событие;
- `publication time` - когда источник это опубликовал;
- `retrieval time` - когда GraphX получил материал;
- `snapshot time` - состояние на дату снимка;
- `system time` - когда запись появилась или изменилась в GraphX.

Их нельзя заменять одной колонкой `date`.

## Интервалы

Интервалы трактуются как `[valid_from, valid_to)`: начало включено, конец не включён. Если граница неизвестна, хранится `NULL` и отдельное основание. `valid_to = NULL` означает «конец неизвестен», а не «действует сейчас».

Для границ хранятся:

- значение;
- точность: `day`, `month`, `year`, `approximate`, `unknown`;
- основание: `explicit`, `event_derived`, `snapshot`, `computed`, `unknown`.

Значение границы хранится в PostgreSQL как каноническая дата-якорь:

- `day` - указанная точная дата;
- `month` - первый день известного месяца;
- `year` - 1 января известного года;
- `approximate` - наиболее обоснованная приблизительная дата;
- `unknown` - значение даты обязательно `NULL`.

Дата-якорь нужна для единообразного хранения и поиска, но не повышает точность источника. API всегда возвращает её вместе с precision, а интерфейс показывает «май 2020», «2020 год» или «примерно 2020», а не придуманную точную дату. Исходная формулировка даты остаётся в исходном значении claim или его qualifiers.

Условие `valid_to > valid_from` обязательно, когда обе границы имеют точность `day`. Для менее точных границ приложение отклоняет только заведомо невозможный порядок; равные якоря сами по себе не означают ошибку. Из неточных границ нельзя автоматически вычислять точную длительность или непрерывность.

## Снимок не равен интервалу

Запись в реестре на конкретную дату доказывает состояние только на дату снимка. Два снимка нельзя автоматически соединять непрерывной линией, если источник не подтверждает период между ними.

## События

Назначение и прекращение полномочий лучше представлены событиями. Из надёжной пары событий можно получить интервал роли, но производный интервал обязан ссылаться на исходные claims и правило вычисления.

Отдельные таблицы `events` и `event_claims` вводятся после проверки данных KASE. До этого claim вида `event` хранит событие без преждевременной универсальной модели.

## Конфликты

Противоречащие даты не затирают друг друга. Они остаются отдельными claims с собственными источниками и точностью. Каноническая проекция может выбрать предпочтительный вариант, но интерфейс должен показать конфликт и объяснить выбор.

## Проверочные сценарии

- известны точные начало и конец роли;
- известен только год назначения;
- есть только снимок состава органов управления;
- два источника называют разные даты прекращения;
- событие опубликовано позже даты самого события;
- документ получен значительно позже публикации;
- новый снимок не доказывает непрерывность между снимками;
- ошибочное entity resolution отменено, и timeline пересобран.
