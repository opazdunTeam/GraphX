# Поток данных

## Первый поиск

1. Пользователь создаёт расследование и вводит человека или организацию.
2. Go API сохраняет расследование, `source_job` и outbox-сообщение в одной транзакции.
3. Outbox publisher отправляет команду в RabbitMQ.
4. Python worker запрашивает источник и сохраняет исходный ответ или документ в MinIO.
5. Worker разбирает данные и публикует результат со ссылками на объекты MinIO либо ссылку на manifest.
6. Go consumer проверяет схему, защищается от повторного сообщения и сохраняет artifact, source records и claims.
7. Из records строятся кандидаты на совпадение.
8. Очевидные случаи обрабатываются автоматически, спорные показываются пользователю.
9. После решения создаются или дополняются канонические сущности.
10. Для подтверждённой сущности планируется обогащение другими источниками.
11. Интерфейс получает компактный граф, timeline и ссылки на доказательства.

## Два этапа исследования

Сначала выполняется `subject_discovery`: система ищет именно исходный объект и не расширяет граф. После подтверждения личности начинается `enrichment` - поиск связей и дополнительной информации о выбранной сущности.

Это важно: без такой границы ошибка в первом совпадении быстро размножится по всему графу.

## Частичный результат

Недоступность одного источника не делает всё расследование неуспешным. Каждый источник имеет собственное состояние, а итог расследования может быть `completed_partial`. Пользователь должен видеть:

- какие источники успешно ответили;
- где ничего не найдено;
- где нужна помощь пользователя;
- где произошла временная или постоянная ошибка.

## Повторная обработка

Исходный artifact не меняется. Новый parser или mapper создаёт новый `processing_run`, новые records и claims. Старый успешный запуск остаётся для аудита, но перестаёт быть активной проекцией.

## Отмена и поздние результаты

Отмена расследования прекращает планирование новых заданий и по возможности отменяет текущую работу. Уже доставленный поздний результат можно сохранить для аудита, но нельзя автоматически применять к отменённому расследованию. Для этого результат помечается `applied = false` с причиной.

## Что считается доказательством

Граф и экранные представления - производные данные. Источник истины для конкретного факта - claim, который ведёт к source record, processing run, artifact и исходному объекту в MinIO.

## Вычисленные связи и гипотезы

В MVP вычисленные связи и гипотезы не хранятся как самостоятельные факты. Go-модуль `analysis` строит их при формировании графа из сохранённых сущностей, фактических отношений и claims.

Каждый результат содержит `rule_code`, `rule_version`, идентификаторы входных фактов и понятное объяснение. Пересчёт не изменяет исходные данные. Вычисленная связь появляется, когда формальное правило выполнено полностью; гипотеза используется, когда наблюдение полезно, но доказательств пока недостаточно.

В API они возвращаются отдельно от фактических рёбер и не записываются в `relationships`. Если расчёт при чтении станет слишком дорогим, после MVP можно добавить пересобираемую проекцию, но она не станет источником истины.
