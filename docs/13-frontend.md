# Интерфейс

## Задача интерфейса

Web-приложение не просто рисует граф. Оно должно показывать, что система знает, откуда это известно и где остаётся неопределённость.

Основные экраны MVP:

- создание расследования;
- ход работы и состояния источников;
- очередь спорных совпадений;
- карточка сущности;
- компактный граф;
- timeline;
- просмотр факта и его доказательства.

Экран создания получает перечень источников через `GET /sources`, а не хранит его отдельной константой во frontend. Остальные серверные DTO определены в `contracts/openapi.yaml`; клиентские типы не должны расходиться с ними вручную.

Форма запуска принимает имя, название или один известный идентификатор.
Она предлагает включённые источники поиска для выбранного вида субъекта и отправляет только явно выбранные коды. Числовые лимиты применяет API по конфигурации сервера.
Во время отправки повторное нажатие блокируется. При повторной отправке того же тела в пределах открытой формы используется прежний `Idempotency-Key`.
Ответ `202 Accepted` открывает экран статуса с идентификатором и подтверждением приёма.

## Состояние расследования

Экран читает `GET /investigations/{investigation_id}/status`. Он показывает агрегированные состояния источников, число попыток, время последнего изменения и следующей попытки, безопасное описание последней проблемы. Сводка `partial_result` показывает число заданий и источников, уже давших результат. В карточке источника отображается его `succeeded_job_count`, даже если другие задания этого источника ещё выполняются. При сбое обновления экран сохраняет последнюю полученную сводку вместе с прогрессом.

Прогресс показан текущим этапом и числом завершённых заданий из известных. Интервал опроса составляет 2–3 секунды в видимой вкладке и 10–15 секунд в скрытой, со случайной задержкой в каждом диапазоне. После временной ошибки или некорректного ответа `2xx` интервал растёт в пределах восьмикратного базового значения и сбрасывается при успехе. Опрос прекращается при терминальном состоянии расследования или постоянной ошибке. При смене расследования или выходе со страницы текущий запрос отменяется.

## Подтверждение совпадений

Review показывает исходную запись, кандидатов, совпавшие признаки, конфликты и доказательства. Score можно отображать как техническую подсказку, но не как «вероятность совпадения».

Пользователь может:

- выбрать существующую сущность;
- указать, что ни один кандидат не подходит;
- отменить ранее принятое решение.

## Граф

По умолчанию граф компактный: только сущности текущего расследования и фактические связи. Вычисленные связи и гипотезы имеют другой вид и отдельный переключатель. Любое ребро открывает claims и оригинальный материал.

Расширение узла выполняется явной командой пользователя и учитывает лимиты глубины и размера.

## Клиентское и серверное состояние

Сервер владеет расследованием, заданиями, reviews, сущностями и графом. Клиент хранит только состояние интерфейса: выбранные узлы, фильтры, открытые панели и кэш ответов. Нельзя считать локальный progress или принятое решение источником истины.

Page components не вызывают `fetch`, не импортируют generated OpenAPI types и не копируют один ответ одновременно в локальные refs и Pinia. HTTP transport и `application/problem+json` изолированы в `shared/api`; request lifecycle и polling принадлежат use-case composable. Pinia используется для UI state или явно определённого кэша, который всегда можно восстановить повторным чтением API.

Общий layout и loading/empty/error states находятся в `shared/ui`. Ошибка отдельного запроса не должна скрывать уже полученный partial result. Отмена запроса при смене страницы отличается от ошибки API и не показывается как отказ источника.

## Технологии

Vue 3, Vite, TypeScript и `pnpm`. Nuxt и SSR не нужны. Polling достаточно для MVP; SSE добавляется позже, если измерения покажут заметную нагрузку или плохой пользовательский опыт.
