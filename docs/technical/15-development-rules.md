# Правила разработки

## 1. Ответственность

### Технический лидер / fullstack

- архитектура, ADR и контракты;
- схема данных и интеграция компонентов;
- каркас Vue-приложения;
- CI/CD и сквозные сценарии;
- ревью изменений границ системы;
- совместная реализация первого эталонного адаптера.

### Go-разработчик

- каркас API;
- investigations/jobs/outbox;
- PostgreSQL repositories и миграции;
- канонические entities/relationships;
- идемпотентность consumers;
- интеграционные тесты Go-контура.

### Python/Go-разработчик

- runtime и SDK воркеров;
- адаптеры первых источников;
- MinIO artifacts;
- HTML/PDF/document parsing;
- fixtures и smoke-тесты источников;
- участие в ingest-контрактах.

Ответственность означает ведение области, но не исключительное право изменения. Изменение контракта ревьюят обе затронутые стороны.

## 2. Порядок первой итерации

1. Зафиксировать OpenAPI для создания/статуса расследования.
2. Зафиксировать сообщения `source.collect.requested/completed`.
3. Поднять PostgreSQL, RabbitMQ и MinIO локально.
4. Реализовать Go API + outbox.
5. Реализовать Python runtime и fixture adapter.
6. Провести один artifact/record/claim до API результата.
7. Подключить первый реальный источник.
8. Добавить минимальный Vue flow.
9. Только после сквозного теста подключать второй источник.

## 3. Ветвление и review

- Основная ветка должна оставаться запускаемой.
- Изменение выполняется небольшим pull request с одной целью.
- Минимум один участник ревьюит код; контракты и миграции ревьюит tech lead.
- Запрещены незадокументированные breaking changes.
- ADR обновляется в том же PR, который меняет принятое решение.
- Генерируемые файлы обновляются вместе с источником генерации.

## 4. Стиль и качество

- Go: стандартный formatter, static analysis и явная обработка ошибок.
- Python: formatter, lint, type checking для контрактов и ядра SDK.
- TypeScript: strict mode, lint и formatter.
- Ошибки на границах преобразуются в контрактные коды.
- Комментарий объясняет причину, а не пересказывает строку кода.
- Новая зависимость добавляется только при понятной пользе и проверенной лицензии.

Конкретные инструменты форматирования фиксируются в конфигурации репозитория при создании приложений.

## 5. Definition of Done

Задача завершена, если:

- выполнены критерии задачи;
- обновлены контракты и документация при изменении поведения;
- добавлены необходимые тесты;
- логирование не раскрывает данные;
- повтор асинхронной операции безопасен;
- обработаны пустой результат и ошибка;
- код проходит CI;
- изменение проверено локально в сквозном сценарии, если затрагивает несколько компонентов.

## 6. Решения и эксперименты

Неопределённое решение сначала проверяется коротким spike с измеримым вопросом. Spike не становится production-кодом автоматически. Результат фиксируется ADR: контекст, варианты, решение, последствия и условия пересмотра.

## 7. Запрет преждевременной сложности

До подтверждённой потребности не добавляются:

- новый deployable service;
- отдельная графовая или поисковая БД;
- Kubernetes;
- собственная система авторизации;
- обязательная LLM-зависимость;
- универсальный workflow engine;
- абстракция, имеющая только одну реализацию и не отделяющая внешнюю зависимость.

Запрет не распространяется на интерфейсы, изолирующие PostgreSQL, RabbitMQ, MinIO и конкретные источники.
