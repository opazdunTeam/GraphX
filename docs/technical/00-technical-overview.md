# Технический обзор

## 1. Назначение архитектуры

Архитектура должна позволить трём разработчикам провести данные от источника до проверяемого результата, не создавая заранее инфраструктуру полноценной коммерческой платформы. Основной объект разработки — контур получения, сохранения, нормализации, сопоставления и темпоральной обработки данных.

MVP не включает регистрацию, вход, роли, оплату, сложную административную панель, полноценный конструктор отчётов и развитое визуальное оформление. Интерфейс обязан быть функциональным: начать расследование, показать состояние источников, дать выбрать неоднозначного кандидата и представить сущности, связи, время и доказательства.

## 2. Архитектурный подход

- Go API реализуется как модульный монолит, а не набор мелких сервисов.
- Получение и разбор данных выполняются независимыми Python-воркерами из одного пакета с общим SDK.
- Асинхронные задания и результаты передаются через RabbitMQ.
- PostgreSQL является источником истины для структурированных данных.
- Исходные документы и ответы источников сохраняются в MinIO.
- Vue-клиент работает с Go API по REST/JSON.
- Внутренняя модель отделена от форматов конкретных источников.
- Любой подтверждённый факт имеет происхождение и доступное доказательство.
- Неоднозначность сохраняется и предъявляется пользователю, а не скрывается автоматическим выбором.

## 3. Стек MVP

| Область | Решение MVP | Комментарий |
|---|---|---|
| Основной API | Go, Gin | Выбор фиксируется ADR; бизнес-логика не зависит от HTTP-фреймворка |
| Доступ к PostgreSQL | `pgx`, SQL; генерация через `sqlc` допустима | Без тяжёлого ORM и скрытых запросов |
| Миграции | `goose`, вручную написанный SQL | Миграции хранятся в репозитории и запускаются отдельно от API |
| Сбор и разбор | Python 3, Pydantic, HTTP-клиент, библиотеки HTML/PDF | Один пакет, несколько consumer-процессов |
| Браузер | Playwright | Только для источников без устойчивого Bulk/API/HTTP-доступа |
| Очереди | RabbitMQ | Команды, результаты, повторы и DLQ |
| Основная БД | PostgreSQL + `pg_trgm` | Канонические и промежуточные структурированные данные |
| Файлы | MinIO, S3 API | Неизменяемые исходные материалы и производные файлы |
| Интерфейс | Vue 3, Vite, TypeScript | SPA без SSR на MVP |
| Контракты | OpenAPI, JSON Schema; позднее AsyncAPI | Версионируемые границы компонентов |
| Развёртывание | Docker Compose, GitHub Actions, Nginx | Один VPS, возможность blue-green |

Gin выбран как стартовый вариант из-за знакомого команде способа разработки и достаточного набора готовых средств. Производительность Gin или chi не является определяющим фактором. Замена HTTP-адаптера не должна затрагивать прикладные сценарии.

## 4. Прикладные компоненты

1. **Web** — минимальный интерфейс расследования.
2. **API** — управление расследованием, каноническими данными, решениями пользователя и выдачей результата.
3. **Workers** — получение материалов, разбор документов и преобразование форматов источников в общие контракты.

Инфраструктура: PostgreSQL, RabbitMQ, MinIO и reverse proxy. Отдельная графовая БД, поисковый кластер, Redis и Kubernetes в MVP не используются.

## 5. Источники MVP

Первая техническая итерация подключает минимальное число источников, необходимое для доказательства сквозного контура:

1. ICIJ или OpenSanctions — первый эталонный адаптер;
2. второй из этой пары — проверка повторного использования SDK;
3. OpenCorporates — переход между человеком и организациями.

КГД и KASE остаются целевыми источниками MVP согласно продуктовой документации, но подключаются после устойчивого сквозного контура. Для историчности приоритет имеет KASE. Точный порядок может измениться после проверки доступа и лицензий.

## 6. Основные ограничения

- один развёрнутый экземпляр продукта без пользовательских учётных записей;
- доступ к демонстрации ограничивается на уровне reverse proxy и сети;
- автоматическая глубина поиска — не более двух переходов;
- граф формируется из PostgreSQL и выдаётся как DTO; отдельная графовая БД отсутствует;
- документы обрабатываются Python-воркерами;
- LLM не является источником фактов и не входит в обязательный контур;
- отказ одного источника не завершает всё расследование ошибкой;
- семантика доставки сообщений — `at least once`, поэтому обработчики идемпотентны.

## 7. Условия выделения новых сервисов

Компонент выделяется из модульного монолита только при наличии хотя бы одной причины:

- независимое масштабирование подтверждено измерениями;
- требуется отдельный цикл релиза;
- компонент использует существенно отличающиеся ресурсы или модель безопасности;
- сбой компонента необходимо изолировать;
- его граница и контракт уже стабильны.

До выполнения этих условий новый модуль остаётся внутри Go API либо пакета Python-воркеров.
