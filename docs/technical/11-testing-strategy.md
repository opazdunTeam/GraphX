# Стратегия тестирования

## 1. Цели

Тестирование в первую очередь защищает:

- происхождение факта;
- отсутствие ложного автоматического объединения;
- корректность временных границ;
- повторяемость обработки сообщения;
- устойчивость к изменению формата источника;
- частичный результат при отказе одного компонента.

Процент покрытия сам по себе не является критерием качества.

## 2. Уровни

### Unit

- предметные инварианты Go;
- нормализация и scoring;
- parser/mapper Python на fixture;
- Vue composables и компоненты сложных состояний.

### Contract

- запросы и ответы соответствуют OpenAPI;
- сообщения соответствуют JSON Schema;
- все адаптеры возвращают общий CollectResult;
- текущая и предыдущая версия сообщения принимаются в период миграции.

### Integration

Запускаются реальные PostgreSQL, RabbitMQ и MinIO в контейнерах:

- транзакции и ограничения БД;
- outbox publisher;
- повторная доставка;
- retry/DLQ;
- загрузка и проверка hash артефакта;
- миграции с пустой и предыдущей схемы.

### End-to-end

Минимальные сценарии:

1. создать расследование;
2. получить данные fixture-источника;
3. выбрать неоднозначного кандидата;
4. увидеть сущность, связь, период и evidence;
5. пережить отказ второго источника;
6. повторить сообщение без дублирования результата.

### Smoke источников

Живые источники проверяются по расписанию или вручную отдельно от обязательного CI. Такой тест обнаруживает изменение сайта/API, но не должен делать каждый pull request нестабильным.

## 3. Fixtures

- Хранятся только публично допустимые и минимизированные данные.
- Секреты, cookies и лишние персональные данные удаляются.
- Исходный fixture не подгоняется под parser без объяснения.
- Fixture содержит metadata: источник, дата получения, версия формата и ожидаемые claims.
- Для документов сохраняются ожидаемые страницы/локаторы доказательств.

## 4. Golden dataset

Отдельный контрольный набор используется для entity resolution и темпоральности. Эталонная разметка проверяется вручную и версионируется. Метрики:

- recall генерации кандидатов;
- precision автоматических объединений;
- число случаев ручной проверки;
- точность извлечения дат/ролей;
- доля фактов с доступным evidence.

Ложное auto-merge считается более тяжёлой ошибкой, чем лишняя ручная проверка.

## 5. CI gates

Pull request обязан пройти:

- форматирование и lint;
- unit tests затронутых приложений;
- проверку OpenAPI/JSON Schema;
- contract tests;
- миграции на чистой БД;
- сборку Docker images;
- небольшой интеграционный сквозной тест.

Полный golden dataset и browser E2E могут запускаться отдельным workflow, если их длительность мешает обратной связи.

## 6. Definition of Done для источника

- карточка источника актуальна;
- есть fixture и тесты parser/mapper;
- сохраняется artifact и evidence locator;
- ошибки классифицированы;
- повтор безопасен;
- живой smoke-тест документирован;
- источник проходит один контрольный сценарий от запроса до интерфейса.
