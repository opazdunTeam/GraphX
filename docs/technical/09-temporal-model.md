# Темпоральная модель

## 1. Виды времени

Система хранит раздельно:

- **время действия** — когда факт или отношение справедливо в предметной области;
- **время события** — когда произошло назначение, увольнение, регистрация и т. п.;
- **дата публикации** — когда источник опубликовал материал;
- **дата получения** — когда система сохранила материал;
- **подтверждено на дату** — снимок состояния по документу;
- **системное время** — когда запись создана или изменена в системе.

Дата публикации не используется как дата назначения, если документ этого не утверждает.

## 2. Интервал действия

Для временного утверждения или отношения хранятся:

```text
valid_from
valid_to
valid_from_precision
valid_to_precision
valid_from_basis
valid_to_basis
```

Точность:

- `day`;
- `month`;
- `year`;
- `approximate`;
- `unknown`.

Основание:

- `explicit` — прямо указано источником;
- `event_derived` — граница выведена из подтверждённого события;
- `snapshot` — известно только состояние на дату документа;
- `computed` — получено формальным правилом;
- `unknown`.

## 3. Открытые и неизвестные границы

- `valid_to = null` не означает автоматически «занимает должность сейчас».
- Текст «по настоящее время» ограничивается датой публикации или подтверждения документа.
- Snapshot подтверждает состояние на дату, но не доказывает начало и окончание периода.
- Полностью неизвестный период остаётся связью без временного интервала и показывается отдельно.

## 4. События

Назначение и прекращение полномочий представляются самостоятельными событиями. Пара совместимых событий может сформировать интервал отношения:

```text
2018-05-10 APPOINTED(person, company, director)
2021-03-01 TERMINATED(person, company, director)
→ relationship valid [2018-05-10, 2021-03-01)
```

Если найдено только назначение, правая граница остаётся неизвестной. Если документ в 2020 году перечисляет действующего директора, создаётся snapshot на 2020 год, а не назначение в 2020 году.

## 5. Пересечение периодов

Вычисленная связь через общую организацию допускается только с явным описанием времени:

- доказанное пересечение — интервалы пересекаются;
- возможное пересечение — одна или обе границы неизвестны;
- пересечения нет — доказанные интервалы не пересекаются.

Возможное пересечение не показывается как доказанный совместный период.

## 6. Конфликты

Противоречащие даты не перезаписывают друг друга. Claims сохраняются отдельно, а отношение получает признак конфликта. API отдаёт:

- конкурирующие значения;
- источники каждого значения;
- применённое правило выбора для представления;
- отсутствие выбора, если правило недостаточно.

## 7. Хранение

В первой миграции используются отдельные поля дат и точности: они проще для частично известных границ и объяснений. PostgreSQL range types можно добавить как вычисляемое/производное представление для запросов пересечения после стабилизации модели.

Для всех таблиц происхождения сохраняются `created_at`; изменяемые канонические проекции имеют `updated_at`. История решений и объединений append-only.

## 8. Выдача

Timeline DTO содержит:

- событие или отношение;
- начало/окончание и точность;
- тип основания;
- уровень результата;
- доказательства;
- предупреждения о неизвестности и конфликте.

Интерфейс не рисует непрерывную линию между точками snapshot без доказанного периода.

## 9. Проверки

Обязательные сценарии:

- точные начало и конец;
- известен только год;
- открытая правая граница;
- snapshot без начала;
- две конфликтующие даты;
- назначение и прекращение из разных источников;
- отношения без дат;
- пересечение и отсутствие пересечения ролей.
