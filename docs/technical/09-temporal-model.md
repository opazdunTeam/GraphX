# Темпоральная модель

## 1. Виды времени

Система хранит раздельно:

- **время действия** — когда факт или отношение справедливо в предметной области;
- **время события** — когда произошло назначение, увольнение, регистрация и т. п.;
- **дата публикации** — когда источник опубликовал материал;
- **дата получения** — когда система сохранила материал;
- **подтверждено на дату** — снимок состояния по документу;
- **audit timestamp** — когда исходная или производная строка записана/изменена в системе; это не полная bitemporal system-time history.

Дата публикации не используется как дата назначения, если документ этого не утверждает.

## 2. Интервал действия

Для временного утверждения или отношения хранятся:

```text
valid_from
valid_to
valid_from_precision
valid_to_precision
valid_from_basis
valid_to_basis
snapshot_at
snapshot_precision
```

Точность:

- `day`;
- `month`;
- `year`;
- `approximate`;
- `unknown`.

Основание:

- `explicit` — прямо указано источником;
- `event_derived` — граница выведена из подтверждённого события;
- `snapshot` — известно только состояние на дату документа;
- `computed` — получено формальным правилом;
- `unknown`.

## 3. Открытые и неизвестные границы

- `valid_to = null` не означает автоматически «занимает должность сейчас».
- Текст «по настоящее время» создаёт snapshot на дату публикации/подтверждения документа, но не записывает эту дату как окончание отношения.
- Snapshot подтверждает состояние на дату, но не доказывает начало и окончание периода.
- Полностью неизвестный период остаётся связью без временного интервала и показывается отдельно.

Если источник одновременно явно сообщает дату начала и состояние «по настоящее время», `valid_from` хранит доказанное начало, `valid_to` остаётся неизвестным, а `snapshot_at` хранит последний момент подтверждения. Интерфейс формулирует это как «началось тогда-то, подтверждено на такую-то дату; дальнейшее состояние неизвестно».

## 4. Семантика границ и точности

- `valid_from` включается в период, `valid_to` исключается: `[valid_from, valid_to)`.
- Точная дата прекращения полномочий становится исключающей `valid_to` этого дня.
- Номинальное неточное значение сохраняется вместе с precision и исходной формулировкой. Например, `2021` не превращается необратимо в точную дату события.
- Для сравнения интервалов отдельная функция получает минимальную/максимальную возможную границу по precision. Query bound является производным значением и не подменяет сохранённую дату.
- `approximate` не участвует в доказанном пересечении без предупреждения.

## 5. События

Назначение и прекращение полномочий представляются самостоятельными событиями. Пара совместимых событий может сформировать интервал отношения:

```text
2018-05-10 APPOINTED(person, company, director)
2021-03-01 TERMINATED(person, company, director)
→ relationship valid [2018-05-10, 2021-03-01)
```

Если найдено только назначение, правая граница остаётся неизвестной. Если документ в 2020 году перечисляет действующего директора, создаётся snapshot на 2020 год, а не назначение в 2020 году.

## 6. Пересечение периодов

Вычисленная связь через общую организацию допускается только с явным описанием времени:

- доказанное пересечение — интервалы пересекаются;
- возможное пересечение — одна или обе границы неизвестны;
- пересечения нет — доказанные интервалы не пересекаются.

Возможное пересечение не показывается как доказанный совместный период.

## 7. Конфликты

Противоречащие даты не перезаписывают друг друга. Claims сохраняются отдельно, а отношение получает признак конфликта. API отдаёт:

- конкурирующие значения;
- источники каждого значения;
- применённое правило выбора для представления;
- отсутствие выбора, если правило недостаточно.

## 8. Хранение

В первой миграции временные поля находятся в claims и relationships. KASE сначала проверяет event claims, snapshot и evidence на реальных документах. Отдельная таблица `events` добавляется, когда начинается самостоятельная materialization событий; до этого timeline строится из утверждений и границ отношений. Это не мешает хранить дату назначения как event claim и позднее материализовать её без повторного обращения к источнику.

Используются отдельные поля дат, точности и основания: они проще для частично известных границ и объяснений. PostgreSQL range types можно добавить как вычисляемое/производное представление для запросов пересечения после стабилизации модели.

Для всех таблиц происхождения сохраняются `created_at`; изменяемые канонические проекции имеют `updated_at`/`superseded_at`. Эти поля служат аудитом обработки, но не обещают восстановить полное состояние всей БД на произвольный системный момент. История processing runs, claims, mappings и решений сохраняется append-only.

## 9. Выдача

Timeline DTO содержит:

- событие или отношение;
- начало/окончание и точность;
- тип основания;
- уровень результата;
- доказательства;
- предупреждения о неизвестности и конфликте.

Интерфейс не рисует непрерывную линию между точками snapshot без доказанного периода.

## 10. Проверки

Обязательные сценарии:

- точные начало и конец;
- известен только год;
- открытая правая граница;
- snapshot без начала;
- две конфликтующие даты;
- назначение и прекращение из разных источников;
- отношения без дат;
- пересечение и отсутствие пересечения ролей.
- явное начало вместе с «по настоящее время» в старом документе;
- snapshot не создаёт ложное событие прекращения;
- year/month precision не превращается в точный день;
- повторная обработка меняет интерпретацию даты, сохраняя прежний processing run.
