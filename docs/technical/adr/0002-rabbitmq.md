# ADR-0002. RabbitMQ для асинхронной работы

- **Статус:** accepted
- **Дата:** 2026-09-19
- **Владельцы:** project-team

## Контекст

Обращение к источникам и обработка документов выполняются долго, имеют разные требования к ресурсам и должны переживать временные ошибки. Go и Python должны участвовать в одном асинхронном процессе.

## Решение

Использовать RabbitMQ для команд и событий. Состояние заданий хранить в PostgreSQL. Принять доставку `at least once`, идемпотентные consumers, retry queues, DLQ и transactional outbox.

## Рассмотренные варианты

- таблица PostgreSQL как очередь;
- Redis/Celery;
- NATS JetStream;
- синхронные HTTP-вызовы.

## Последствия

- появляется отдельный инфраструктурный компонент;
- необходимы мониторинг очередей и дисциплина схем сообщений;
- Python и Go остаются равноправными consumers;
- RabbitMQ не используется как база результата.

## Условия пересмотра

Неподходящие эксплуатационные свойства при измеренной нагрузке или появление требований к журналу событий, которым RabbitMQ не соответствует.
