# ADR-0010. Polling в MVP и развитие через ETag/SSE

- **Статус:** accepted
- **Дата:** 2026-10-01
- **Владельцы:** tech-lead

## Контекст

Сбор данных выполняется асинхронно и может занимать минуты. Интерфейсу нужны редкие односторонние обновления этапа, прогресса и необходимости выбора кандидата. MVP разворачивается одним экземпляром API и не требует инфраструктуры постоянных соединений.

## Решение

В MVP использовать polling компактного status endpoint раз в 2–3 секунды. Endpoint читает PostgreSQL и не вызывает RabbitMQ, workers или источники. Клиент применяет jitter/backoff, замедляется в скрытой вкладке и прекращает polling в конечном состоянии.

Сразу хранить и возвращать монотонную `state_version`. После MVP на её основе могут быть добавлены ETag/`If-None-Match`, а затем SSE как уведомление об изменении версии. После SSE-события и переподключения клиент получает состояние обычным GET.

## Рассмотренные варианты

- WebSocket;
- SSE с первой версии;
- webhook;
- синхронное ожидание окончания в исходном HTTP-запросе.

## Последствия

- MVP получает простой и устойчивый клиентский сценарий;
- каждый открытый экран создаёт периодические HTTP-запросы;
- status read-модель должна оставаться компактной и индексируемой;
- ETag уменьшит тело неизменившихся ответов, но не количество запросов;
- SSE не становится источником истины и может внедряться отдельно;
- webhook остаётся механизмом будущей server-to-server интеграции, а не обновления браузера.

## Условия пересмотра

Измеренная нагрузка polling, требование почти мгновенных уведомлений или переход к нескольким экземплярам API с подготовленным распространением SSE-событий.
