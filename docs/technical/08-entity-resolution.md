# Сопоставление сущностей

## 1. Разделение задач

Система различает:

1. **Нечёткий поиск** — получить ограниченный список кандидатов.
2. **Entity resolution** — решить, относятся ли записи к одному объекту.
3. **Выявление связей** — определить отношения между уже различёнными объектами.

Похожее имя не является достаточным основанием для объединения и не доказывает родство.

В начале расследования дополнительно выполняется **разрешение исходного субъекта**: система сначала определяет, какого именно найденного человека или организацию имел в виду пользователь, и только затем запускает полный сбор. Это частный случай entity resolution, оформленный `match_review` типа `initial_subject`.

## 2. Нормализация

Для человека сохраняются исходное значение и производные представления:

- Unicode normalization;
- приведение регистра;
- нормализация пробелов и пунктуации;
- разделение фамилии, имени, отчества при достаточной уверенности;
- варианты порядка компонентов;
- инициалы;
- транслитерации кириллица↔латиница;
- источник каждого варианта.

Для организаций дополнительно:

- отделение организационно-правовой формы;
- нормализация кавычек и сокращений;
- сохранение юридического названия;
- юрисдикция и регистрационный идентификатор.

Нормализация не исправляет исходную запись и не пытается угадать отсутствующее значение.

## 3. Генерация кандидатов

Единицей сопоставления является `source_record`, описывающая человека или организацию. Claims этой записи предоставляют имена, идентификаторы, даты и связи как признаки. Отдельный claim не сопоставляется с entity самостоятельно.

Сначала применяются дешёвые блокирующие признаки:

- точный идентификатор в той же области;
- совпадение нормализованной фамилии/названия;
- trigram similarity имени;
- транслитерированный вариант;
- дата/год рождения;
- юрисдикция;
- связанная организация.

PostgreSQL `pg_trgm` используется для формирования top-N кандидатов. Значение similarity является признаком, а не вероятностью и не окончательным решением.

## 4. Признаки решения

Положительные признаки:

- один и тот же устойчивый идентификатор;
- совпадение полного имени и даты рождения;
- несколько независимых вариантов имени;
- совпадающая организация и роль в совместимом периоде;
- общий адрес, телефон или домен при достаточной специфичности.

Конфликты:

- разные уникальные идентификаторы;
- несовместимые даты рождения;
- взаимоисключающие юрисдикции или события;
- одновременные несовместимые должности, если это действительно ограничение роли;
- явное указание источника на разных лиц.

Каждый feature хранится с кодом, значением, вкладом в score и ссылками на claims.

## 5. Правила MVP

- Совпадение уникального идентификатора без конфликта может разрешить автоматическое объединение.
- Несколько сильных независимых признаков могут разрешить объединение после калибровки на контрольном наборе.
- Одно имя, инициалы или транслитерация никогда не разрешают auto-merge.
- Средняя зона создаёт review для пользователя.
- Явный сильный конфликт блокирует автоматическое объединение независимо от текстового score.
- Пороговые значения не фиксируются до измерения контрольной выборки.

Наличие одного кандидата не считается сильным признаком. Такой кандидат выбирается автоматически только при выполнении правила автовыбора; иначе пользователь получает review даже с одной слабой записью.

## 6. Разрешение исходного субъекта

1. Discovery-источники ищут ограниченный набор возможных контрагентов по исходным данным.
2. Шлюз решения срабатывает после обязательных discovery-заданий, ограниченного тайм-аута либо точного идентификатора без конфликта.
3. Кандидаты фиксируются внутри версионированного `match_review`.
4. Сильное правило создаёт автоматический decision; неоднозначный случай требует выбора пользователя.
5. Decision выбирает запись, создаёт или переиспользует корневую entity и автоматически планирует enrichment.

Discovery-артефакты и записи сохраняются и используются на следующих этапах. Повторный сетевой запрос к тому же материалу не является частью обычного продолжения.

## 7. Объяснимость

Кандидат возвращается в виде:

```json
{
  "score": 0.73,
  "algorithm_version": "person-match/0.1.0",
  "supporting_features": [
    {"code": "NAME_TRANSLITERATION_MATCH", "weight": 0.28},
    {"code": "SHARED_ORGANIZATION", "weight": 0.18}
  ],
  "conflicts": [
    {"code": "BIRTH_DATE_MISSING", "severity": "warning"}
  ],
  "recommendation": "review"
}
```

Пользователь видит понятное описание, а не только число.

## 8. Решение и отмена

Решение append-only: отмена создаёт новое решение со ссылкой `supersedes_id`. Клиент передаёт ожидаемую `lock_version`, поэтому устаревший экран не может разрешить уже пересчитанный review. Принятое решение создаёт актуальный `entity_records` mapping между записью источника и сущностью.

При ошибке mapping закрывается через `unlinked_at`. Затем в той же application operation либо гарантированно поставленной внутренней работе выполняется ограниченная пересборка затронутых проекций:

1. выбираются claims актуальных успешных processing runs;
2. участвуют только subject/object records с активными mappings;
3. заново определяются допустимые names, identifiers и factual relationships затронутых entities;
4. проекция без оставшихся оснований помечается superseded и исключается из текущей read-модели;
5. relationship с другим допустимым supporting claim сохраняется;
6. derived links/hypotheses расследования пересчитываются из обновлённого factual слоя.

Artifacts, source records, claims и история решений не удаляются. В MVP не выполняется физическое слияние entities через перенос всех данных и рёбер; такая операция и необходимые для неё поля проектируются отдельным post-MVP решением.

## 9. Контроль качества

Golden dataset должен содержать:

- кириллицу и латиницу;
- перестановку компонентов ФИО;
- инициалы;
- распространённые транслитерации;
- однофамильцев;
- конфликт дат рождения;
- совпадение компании при различии людей;
- реальные тестовые случаи Клебанова Александра Яковлевича и Турлова Тимура Руслановича с вручную проверенной разметкой.

Минимальная версия golden dataset создаётся до настройки весов и порогов. Она расширяется вместе с каждым новым источником; пример, использованный для настройки правила, не считается независимой проверкой этого правила.

Измеряются precision/recall генерации кандидатов отдельно от качества окончательного merge. Особое внимание уделяется ложным автоматическим объединениям.

Обязательный regression-сценарий отмены: ошибочно связать record A с entity X, материализовать имя и отношение, отменить mapping, убедиться, что неподтверждённые имя/отношение исчезли, другой supporting claim сохранил общий факт, а исходный claim по-прежнему доступен как история.

## 10. LLM и embeddings

Они не нужны в первой версии. Позднее их можно применять для получения дополнительного признака или объяснения неоднозначного случая. Их результат версионируется и не отменяет правила конфликтов, доказательства и пользовательский контроль.
