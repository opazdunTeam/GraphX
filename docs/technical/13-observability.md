# Наблюдаемость

## 1. Цели MVP

Команда должна ответить:

- где находится расследование;
- какой источник или этап задерживается;
- почему задание повторяется;
- какое сообщение создало запись;
- какой artifact и parser породили claim;
- почему пользователю показан конкретный результат.

## 2. Логи

Все процессы пишут структурированный JSON в stdout. Обязательные поля по применимости:

```text
timestamp
level
service
version
environment
message
trace_id
correlation_id
message_id
investigation_id
job_id
source_id
artifact_id
duration_ms
error_code
```

ФИО, документы, cookies, токены и полный payload по умолчанию не логируются. Для отладки используются внутренние идентификаторы и безопасные агрегаты.

## 3. Trace context

- HTTP middleware создаёт/принимает `trace_id`.
- Команда RabbitMQ получает тот же `correlation_id` и новый `message_id`.
- Дочернее сообщение указывает `causation_id`.
- Идентификаторы сохраняются в записи задания и outbox.

Полноценная распределённая трассировка через OpenTelemetry может быть добавлена позднее; формат идентификаторов сразу должен быть совместим с таким переходом.

## 4. Метрики

Минимальный набор:

- HTTP request count/latency/errors;
- длина очереди и число unacked сообщений;
- возраст старейшего сообщения;
- число retries и DLQ;
- длительность задания по source/operation;
- success/not_found/unavailable/error по источнику;
- количество обработанных records/claims;
- время от создания расследования до первого результата и завершения;
- число reviews и доля auto-merge.

Значения `investigation_id` и `person_name` не используются как label метрики.

## 5. Алерты demo-окружения

- API не готов;
- PostgreSQL/MinIO/RabbitMQ недоступны;
- DLQ содержит новые сообщения;
- очередь не уменьшается и возраст старейшего задания растёт;
- свободное место ниже порога;
- источник систематически отвечает ошибкой формата/доступа.

Для университетского MVP допустима простая доставка уведомления владельцу проекта без полноценного on-call процесса.

## 6. Аудит

До регистрации достаточно фиксировать системные и пользовательские решения с `actor_type = demo_user`. После появления нескольких пользователей решения, отмены объединений и запуски расширения должны содержать устойчивый `actor_id`.
