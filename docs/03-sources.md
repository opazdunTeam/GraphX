# Источники данных

## Общий подход

Источник подключается не ради количества. Он должен добавить хотя бы одну полезную возможность: обнаружение объекта, устойчивый идентификатор, корпоративную связь, временной контекст или первичное доказательство.

Перед разработкой адаптера проверяются:

- условия использования;
- устойчивость способа доступа;
- покрытие нужной юрисдикции и периода;
- наличие идентификаторов и дат;
- возможность сохранить первичный материал;
- частота обновления;
- цена поддержки адаптера.

## Порядок способов доступа

Предпочтение отдаётся более устойчивому и проверяемому способу:

1. Bulk-набор.
2. Документированный API.
3. Открытый файл или документ.
4. Обычный HTTP-запрос к странице.
5. Автоматизация браузера.
6. Ручная загрузка материала.

## Последовательность добавления источников

| Источник            | Что даёт                                                     | Место в плане               |
| ------------------- | ------------------------------------------------------------ | --------------------------- |
| Fixture             | Повторяемый тест всего контура без сети                      | первый шаг                  |
| ICIJ Offshore Leaks | Люди, организации, посредники, адреса и опубликованные связи | первый реальный источник    |
| KASE                | Раскрытия эмитентов, документы, роли и даты                  | второй реальный источник    |
| OpenSanctions       | Санкционные, PEP и связанные наборы, нормализованные объекты | по доступности после основы |
| КГД Казахстана      | Проверка налогоплательщиков и статусов по ИИН/БИН            | по подтверждённому доступу  |
| OpenCorporates      | Компании и должностные лица разных юрисдикций                | после KASE                  |

SEC EDGAR и RDAP вызываются только для объектов, которым они действительно нужны. Источники других стран относятся к следующему этапу.

## Роли источников

- **Discovery** быстро формирует список возможных исходных объектов.
- **Enrichment** добавляет подробные атрибуты и отношения после выбора объекта.
- **Evidence** предоставляет документ или запись, на которую можно сослаться.
- **Verification** подтверждает идентификатор, статус или отдельное значение.

Один источник может выполнять несколько ролей, но они должны быть указаны в metadata адаптера.

## Что сохраняется

Для каждого обращения сохраняются:

- адрес или внешний идентификатор;
- время получения;
- дата публикации, если она известна;
- MIME type и размер;
- SHA-256;
- версия адаптера;
- безопасные HTTP-метаданные;
- сам исходный материал в MinIO;
- связь материала с заданием.

Повторный разбор использует сохранённый материал. Сетевой запрос не повторяется без причины.

## Наблюдение за источниками

Состояние источника нужно отслеживать, но внешний источник не является обязательной зависимостью готовности всего приложения.

Для каждого адаптера полезны:

- время последнего успешного обращения;
- последняя ошибка и её класс;
- доля успешных запросов;
- изменение формата ответа;
- возраст локального Bulk-набора;
- состояние лимита запросов;
- наличие новых сообщений в DLQ.

Активная проверка запускается редко и безопасным запросом. Она не должна тратить платную квоту или создавать нагрузку. Краткая недоступность одного источника отображается в расследовании как `unavailable`, но не делает весь worker или API неготовым.

## Добавление нового источника

Новый адаптер считается готовым, когда:

1. описаны назначение, способ доступа, ограничения и лицензия;
2. создана обезличенная fixture;
3. исходный материал сохраняется до разбора;
4. parser и mapper имеют версии;
5. ошибки разделены на повторяемые, постоянные и требующие действия;
6. результат проходит JSON Schema;
7. есть тест пустого ответа, изменения формата и повтора сообщения;
8. данные доходят до API и интерфейса;
9. определены безопасные rate limits и timeout;
10. документация каталога обновлена.
