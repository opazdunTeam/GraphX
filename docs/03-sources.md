# Источники данных

## Общий подход

Источник подключается не ради количества. Он должен добавить хотя бы одну полезную возможность: обнаружение объекта, устойчивый идентификатор, корпоративную связь, временной контекст или первичное доказательство.

Перед разработкой адаптера проверяются:

- условия использования;
- устойчивость способа доступа;
- покрытие нужной юрисдикции и периода;
- наличие идентификаторов и дат;
- возможность сохранить первичный материал;
- частота обновления;
- цена поддержки адаптера.

## Порядок способов доступа

Предпочтение отдаётся более устойчивому и проверяемому способу:

1. Bulk-набор.
2. Документированный API.
3. Открытый файл или документ.
4. Обычный HTTP-запрос к странице.
5. Автоматизация браузера.
6. Ручная загрузка материала.

## Последовательность добавления источников

| Источник            | Что даёт                                                     | Место в плане               |
| ------------------- | ------------------------------------------------------------ | --------------------------- |
| Fixture             | Повторяемый тест всего контура без сети                      | первый шаг                  |
| ICIJ Offshore Leaks | Люди, организации, посредники, адреса и опубликованные связи | первый реальный источник    |
| KASE                | Раскрытия эмитентов, документы, роли и даты                  | второй реальный источник    |
| OpenSanctions       | Санкционные, PEP и связанные наборы, нормализованные объекты | по доступности после основы |
| КГД Казахстана      | Проверка налогоплательщиков и статусов по ИИН/БИН            | по подтверждённому доступу  |
| OpenCorporates      | Компании и должностные лица разных юрисдикций                | после KASE                  |

SEC EDGAR и RDAP вызываются только для объектов, которым они действительно нужны. Источники других стран относятся к следующему этапу.

## ICIJ Offshore Leaks

Источник подходит для поиска кандидатов среди организаций из опубликованных офшорных наборов и среди связанных с ними записей типа `Officer`. Наборы покрывают разные исторические периоды. Совпадение имени, связь в базе и отсутствие записи сами по себе не позволяют идентифицировать объект, судить о его текущем статусе или делать вывод о нарушении закона. [Скачать данные](https://offshoreleaks.icij.org/pages/database), [охват и ограничения](https://offshoreleaks.icij.org/pages/faq).

Для первого адаптера выбран локальный индекс из официального ZIP с CSV. Архив загружается отдельно от расследований по HTTPS без ключа. Проверка HTTP Range подтвердила доступность архива. После полной загрузки проверены заголовки CSV и контрольная строка организации в UTF-8. Проверенный снимок занимал 72 783 104 байта, SHA-256 — `84f5b491a1ac11b8d3e4afba4a9a1bebcc42b2e7bdf7c80ec60709ab1776e237`. Ссылка `LATEST` изменяема, поэтому при импорте нужно фиксировать SHA-256 конкретной версии. Импорт должен проверять размер архива и распаковываемых данных. Поиск должен возвращать ограниченное число кандидатов и сохранять различия между одноимёнными записями. [Официальный архив](https://offshoreleaks-data.icij.org/offshoreleaks/csv/full-oldb.LATEST.zip).

| Файл | Поля для первого среза и дальнейшего обогащения |
| --- | --- |
| `nodes-entities.csv` | `node_id`, `name`, `original_name`, `former_name`, `jurisdiction`, `incorporation_date`, `struck_off_date`, `status`, `sourceID`, `valid_until` |
| `nodes-officers.csv` | `node_id`, `name`, `country_codes`, `sourceID`, `valid_until` |
| `relationships.csv` | `node_id_start`, `node_id_end`, `rel_type`, `link`, `start_date`, `end_date`, `sourceID` |

`node_id` — внешний идентификатор записи ICIJ. В GraphX его следует передавать строкой под ключом `icij_node_id`. Для доказательства нужны исходный материал, версия набора, CSV-файл и локатор записи. `sourceID` указывает набор данных, `valid_until` описывает исторический охват источника, а даты регистрации и прекращения относятся к конкретной записи. Поля дат связи относятся к ребру. Пустые даты и неполные связи допустимы.

Документированный Reconciliation API подходит для ручной контрольной проверки формата. `GET /api/v1/reconcile` вернул manifest 0.2 с `batchSize: 25`. `POST /api/v1/reconcile` без токена вернул `201 application/json`. Для одного запроса кандидаты лежат в `result`, для пакетного — в `result` каждой именованной записи. Кандидат содержит строковый `id`, `name`, `types`, `match` и `score`. Вымышленное имя вернуло три похожие записи с `match: false`. Документация указывает размер пакета, а частота запросов отдельно не опубликована. Проверенные ответы не содержали заголовков rate limit. Рабочий поиск в локальном индексе не зависит от доступности этого API. [Документация API](https://offshoreleaks.icij.org/docs/reconciliation).

Контрольная организация BICO-FIN S. A. (`10067217`) совпала при поиске по названию. Запрос карточки `GET /api/v1/rest/nodes/10067217` вернул `200 application/json` с числовым `id` и объектом `properties`. Даты и статус этой компании доступны в CSV и публичной карточке. Контрольный запрос типа `Officer` вернул запись `12161442`, но отметил вариант имени с диакритикой как `match: false`. Для тестов адаптера можно использовать синтетические строки с теми же колонками, включая два одинаковых имени с разными ID, пустые даты, отсутствующую запись и повреждённый CSV. [Карточка организации](https://offshoreleaks.icij.org/nodes/10067217), [карточка Officer](https://offshoreleaks.icij.org/nodes/12161442).

Подключение адаптера к каталогу GraphX относится к [#27](https://github.com/opazdunTeam/GraphX/issues/27). Его запуск зависит от [сквозного теста Fixture #25](https://github.com/opazdunTeam/GraphX/issues/25) и [управляемых повторов и диагностики #54](https://github.com/opazdunTeam/GraphX/issues/54).

## Роли источников

- **Discovery** быстро формирует список возможных исходных объектов.
- **Enrichment** добавляет подробные атрибуты и отношения после выбора объекта.
- **Evidence** предоставляет документ или запись, на которую можно сослаться.
- **Verification** подтверждает идентификатор, статус или отдельное значение.

Один источник может выполнять несколько ролей, но они должны быть указаны в metadata адаптера.

## Что сохраняется

Для каждого обращения сохраняются:

- адрес или внешний идентификатор;
- время получения;
- дата публикации, если она известна;
- MIME type и размер;
- SHA-256;
- версия адаптера;
- безопасные HTTP-метаданные;
- сам исходный материал в MinIO;
- связь материала с заданием.

Архитектура допускает повторный разбор сохранённого материала без нового сетевого запроса. Отдельный контракт такого задания добавляется перед реализацией повторного разбора.

## Наблюдение за источниками

Состояние источника нужно отслеживать, но внешний источник не является обязательной зависимостью готовности всего приложения.

Для каждого адаптера полезны:

- время последнего успешного обращения;
- последняя ошибка и её класс;
- доля успешных запросов;
- изменение формата ответа;
- возраст локального Bulk-набора;
- состояние лимита запросов;
- наличие новых сообщений в DLQ.

Активная проверка запускается редко и безопасным запросом. Она не должна тратить платную квоту или создавать нагрузку. Краткая недоступность одного источника отображается в расследовании как `unavailable`, но не делает весь worker или API неготовым.

## Добавление нового источника

Новый адаптер считается готовым, когда:

1. описаны назначение, способ доступа, ограничения и лицензия;
2. создана обезличенная fixture;
3. исходный материал сохраняется до разбора;
4. parser и mapper имеют версии;
5. ошибки разделены на повторяемые, постоянные и требующие действия;
6. результат проходит JSON Schema;
7. есть тест пустого ответа, изменения формата и повтора сообщения;
8. данные доходят до API и интерфейса;
9. определены безопасные rate limits и timeout;
10. документация каталога обновлена.
