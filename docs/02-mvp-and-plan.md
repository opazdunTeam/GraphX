# MVP и план развития

## Что должен доказать MVP

MVP должен показать, что GraphX ускоряет первичную проверку человека и связанных организаций, не теряя доказательства и не создавая неприемлемого числа ложных объединений.

Демонстрация инфраструктуры, число адаптеров и красота графа сами по себе эту гипотезу не подтверждают.

## Первый вертикальный срез

Первый сценарий должен пройти систему целиком:

1. Пользователь создаёт расследование человека.
2. Go сохраняет расследование, задание и outbox.
3. Fixture-worker получает команду через RabbitMQ.
4. Worker сохраняет исходный материал в MinIO.
5. Результат возвращается в Go.
6. Go регистрирует artifact, processing run, source record и claim.
7. API возвращает частичный результат и доказательство.
8. Vue показывает состояние источника и найденное утверждение.

До завершения этого пути не нужно параллельно строить полный matching, сложный граф или пять адаптеров.

## Демонстрационный MVP

После fixture подключаются реальные источники:

1. ICIJ - первый внешний доказательный контур.
2. KASE - документ, корпоративная роль, снимок и историческое событие.
3. OpenSanctions или КГД - дополнительная идентификация, если доступ устойчив.

OpenCorporates подключается позднее KASE. Состав демонстрации может измениться, если источник недоступен, имеет неподходящие условия или почти не добавляет полезных сведений.

## Что обязательно оставить

- сохранение исходного материала;
- происхождение каждого утверждения;
- частичный результат по источникам;
- двухфазный поиск исходного объекта;
- ручное решение неоднозначности;
- возможность отменить ошибочное сопоставление;
- разделение факта, вычисленной связи и гипотезы;
- временная модель без ложной непрерывности;
- компактная выдача с доказательствами.

## Что не является приоритетом при реализации MVP

- универсальную онтологию всех активов и юрисдикций;
- отдельную графовую базу;
- автоматический отчёт уровня коммерческого продукта;
- сложный конструктор расследований;
- полноценную таблицу событий до проверки event claims на KASE;
- собственную систему пользователей и паролей;
- blue-green развёртывание, если основной сценарий ещё не готов;
- обязательную LLM-обработку;
- микросервисы ради будущего масштаба.

## Проверка гипотезы

До настройки порогов создаётся небольшой вручную размеченный набор примеров. Для каждого контрольного сценария измеряются:

- время ручной проверки без GraphX и с ним;
- полнота найденных релевантных записей;
- доля ложных кандидатов;
- точность автоматических объединений;
- доля результатов с рабочим переходом к доказательству;
- понятность объяснений для специалиста;
- готовность специалиста повторно использовать продукт.

Особенно важны ложные автоматические объединения: редкий пропуск безопаснее уверенного объединения двух разных людей.

## Главные риски MVP

- Источник меняет формат или ограничивает доступ. Поэтому каждый следующий адаптер начинается только после сквозной проверки предыдущего, а исходные ответы сохраняются.
- Два разных человека ошибочно объединяются. Поэтому имя не является достаточным основанием, конфликты блокируют auto-link, а решение можно отменить.
- Модель данных разрастается раньше реальных примеров. Поэтому события, сложная онтология и новые сервисы добавляются после ICIJ и KASE.
- Граф выглядит убедительнее доказательств. Поэтому факт, вычисленная связь и гипотеза различаются и визуально, и в данных.

## Решение после MVP

После проверки выбирается один вариант:

- продолжать развитие текущего ядра;
- сузить сценарий или набор источников;
- изменить целевую аудиторию;
- остановить проект, если экономия времени или качество не подтверждены.

Расширение инфраструктуры начинается только после этого решения.
